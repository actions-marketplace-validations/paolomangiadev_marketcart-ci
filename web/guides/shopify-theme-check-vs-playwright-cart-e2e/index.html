Shopify Theme Check vs Playwright cart E2E: what each one catches

Short answer: Theme Check is a static linter for the Liquid and JSON in your theme; it never runs the theme in a browser. A browser test runs the theme against a store and sees runtime state, such as whether the cart drawer shows what /cart.js stored. They catch different classes of bugs, so run both: Theme Check first (fast, no store), the cart E2E check second.

What each one looks at

Theme CheckCart E2E (Playwright)
Inputtheme source files (Liquid, JSON)a running storefront
Finds (per Shopify's docs / by design)syntax errors, missing templates, unused variables and snippets, unknown and deprecated tags, performance issuesstored cart vs visible drawer: missing line, wrong variant, quantity, price, currency, badge, total
NeedsShopify CLI, no storea store you control (or a fixture), a browser
Cannot seeJavaScript behaviour, section responses at runtime, app scripts, the store's datacode paths it does not exercise; themes it has no adapter for

Shopify CLI runs it as shopify theme check; --fail-level sets the minimum severity that makes the command exit with an error code, and --output selects the output format.

A reproducible case where valid source still shows a stale cart

Dawn's add-to-cart asks /cart/add to return the re-rendered cart-drawer and cart-icon-bubble sections, and cart-drawer.js swaps them in. If a customization renames the drawer section, or an app script replaces the drawer element, every Liquid and JSON file can still be valid while the drawer is no longer updated. The failure lives in JavaScript and in the runtime section response, which is outside what Theme Check analyzes according to its documentation. A browser check sees it immediately. Our synthetic store reproduces the symptom: on the stale-drawer page the add returns 200 and /cart.js has one line, but the drawer shows none; the healthy page is identical except for the swap. We do not claim a Theme Check run on any particular theme here; the point is the category of bug, not a scorecard.

Run both in GitHub Actions

name: theme-quality
on:
  pull_request:
permissions:
  contents: read
jobs:
  theme-check:
    # Static: Liquid and JSON linting of the theme source. No store, no browser, no secrets.
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '22'
      - run: npx --yes @shopify/cli@5.0.1 theme check --path . --fail-level error
  cart-e2e:
    # Runtime: a real browser adds a product and compares /cart.js with the drawer the shopper sees.
    # The demo job proves the runner works with no account; replace it with mode: remote for your store.
    runs-on: ubuntu-latest
    steps:
      - uses: paolomangiadev/marketcart-ci@v0.2.0
        with:
          mode: demo

The cart-e2e job above runs the no-account demo (a synthetic store with planted bugs; it exits 0 when each planted case behaves as expected). For your store use mode: remote with a cases file and the license as a secret (the generator writes it), or check a public store for free on the runner's own browser: npx github:paolomangiadev/marketcart-ci#v0.2.1 check marketcart/cases.json.

Troubleshooting

  • Theme Check fails on warnings you accept: raise --fail-level or configure checks in .theme-check.yml (shopify theme check --init generates one).
  • E2E returns UNSUPPORTED: the theme has no adapter (Dawn family and Horizon 4.4 only) or the requested market was not served. That is "not verified", not a pass.
  • E2E returns BLOCKED: Shopify kept answering HTTP 429; space runs out and do not run many stores in parallel.

Limits

An E2E check only covers the flows it runs (here: add to cart and read the cart surface) and does not find every bug. MarketCart CI supports Dawn-family themes and Horizon 4.4; live-verified so far on a Dawn 16.1.1 cart page.
